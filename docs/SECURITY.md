# 安全模型

## 1. 信任根

| 对象 | 信任来源 | 变更策略 |
| --- | --- | --- |
| 官方下载主机 | `config/releases.json` 中**人工审阅**的精确主机名 | 只接受 HTTPS；任何主机变更必须走代码评审，禁止运行时自动接受 |
| 官方版本清单 schema | `workbuddy-releases-v1`（需实测确认后才启用） | 出现未知关键字段 → 解析失败 → 停止（fail-closed） |
| 安装包签名发布者 | 证据包 `authenticode.subject` | 新证书/新发布者**不会**被自动信任；必须人工核对后更新证据包 |
| 安装包内容 | SHA-256（官方元数据提供时比对） | 哈希不符 → 拒绝写入 |
| 产品身份 | 应用元数据 `applicationName` / `dataFolderName` / 版本 | 任一不符 → `mismatch`，禁止写操作 |

### 证书轮换

1. 新证书出现时，工具报 `E_SIGNER_UNTRUSTED`，**不**下载、**不**安装。
2. 人工核对证书主题、指纹、有效期与官方公告。
3. 更新证据包（`config/evidence.json` 或用户导入的证据），重新走 Task 2 验证。
4. 保留旧证据副本，便于回滚判断。

## 2. 权限边界

- 默认只管理当前 Windows 用户，**不要求管理员权限**。
- 需要提权的官方步骤必须展示原因、命令、目标，由用户单独确认并通过系统 UAC；**不做静默提权**。
- 不伪造点击、不隐藏官方安装器界面、不修改安装包、不重打包二进制、不改产品身份字段。
- 渲染进程：`nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`、CSP `default-src 'none'`、只加载本地资源、禁止导航与 `window.open`。
- IPC：每个通道校验发送方 `webContents.id` 在授权集合内，入参经 zod `strict` 解析，未知字段直接拒绝。
- 权限请求（摄像头、通知、剪贴板等）默认全部拒绝。

## 3. 只读发现与写操作授权分离

只读发现与“是否允许写操作”是两条独立链路，任何检测结果都不能提升写权限：

- 发现来源：卸载登记（HKCU/HKLM 32/64）、登记字段推导、运行中进程可执行路径、桌面/开始菜单快捷方式、有界常见安装位置、用户指定目录。
- 只读边界：不执行 `UninstallString` / `InstallSource` 里的任何命令；不启动快捷方式目标；不枚举整盘；不读取用户数据文件。
  进程查询只按名称过滤并取 `ExecutablePath`，不导出整张进程表。
- 身份判定按可读元数据（`product.json` / `package.json`，含 `app.asar` 内，经 `original-fs` 读取）与已知产品特征比对；
  读不到时标记 `unverified`，读到但与两个产品都不符时标记 `conflict` 并要求人工确认。
- 文件名、目录名、卸载显示名、单一元数据字段、进程名都**只能作为线索**；`identity=identified` 也**不代表**允许写操作。
- 写操作仅由证据门（`capability`）决定；无证据包时恒为 `read-only`，`start()` 仍返回 `E_CAPABILITY_BLOCKED`。

## 4. 路径与文件写入

所有写操作前必须通过 `PathGuard`：

- 必须是绝对路径，且位于用户选择的**管理根目录**之内；
- 拒绝磁盘根、系统目录、用户数据目录、网络共享（MVP）、设备命名空间（`\\?\`、`\\.\`）、8.3 短名；
- 拒绝 `..` 规范化后逃逸、大小写绕过、重解析点（符号链接/junction）逃逸；
- `replace` 步骤必须存在同目标的 `backup` 步骤（**绝不先删旧版再试装新版**）；
- `delete` 步骤必须登记在 `plan.deletionTargets`，且只允许本工具受管目录；
- 暂存目录位于 `<管理根>\.staging\<操作编号>`，校验通过后才提交到 `<管理根>\WorkBuddy-CN\versions\<版本>` 或 `<管理根>\WorkBuddy-AI\versions\<版本>`。

## 5. 操作日志与恢复
- 状态机：`planned → staged → verified → committed`，失败/中断进入 `failed`/`interrupted`，回滚进入 `rolled-back`（终态）。
- 日志写入采用"临时文件 + rename"，避免半个 JSON。
- 崩溃重启后只允许"继续验证"或"回滚"，**禁止**根据猜测状态删除文件。
- 回滚幂等：备份缺失但目标存在时视为已恢复；备份与目标都缺失时返回 `E_ROLLBACK_FAILED` 并要求人工介入。

## 6. 日志隐私

- 不访问、不上传、不记录 WorkBuddy 登录凭据、令牌、聊天内容或用户数据。
- 诊断导出默认把用户主目录替换为 `%USERPROFILE%`、把 `\Users\<name>` 替换为 `\Users\<user>`。
- 含疑似凭据的行（`Bearer ...`、`token=...`、`password=...`、`cookie=...`）整行丢弃。
- 仓库不提交客户端安装包、用户数据、真实机器路径快照、日志中的个人信息或任何密钥（见 `.gitignore`）。

## 7. 失败处理（fail-closed）

| 失败类型 | 行为 |
| --- | --- |
| 来源/主机不可信 | 不发起请求，`E_HOST_NOT_ALLOWED` |
| 响应 schema 变化 | 停止解析，`E_REMOTE_SCHEMA`，保留现有安装 |
| 签名无效 / 发布者不受信 | 拒绝写入，`E_SIGNATURE_INVALID` / `E_SIGNER_UNTRUSTED` |
| 产品身份不符 | 拒绝写入，`E_IDENTITY_MISMATCH` |
| 无法确认（元数据缺失、profile 未验证） | 判定 `unknown`，不执行任何写操作 |
| 路径不可信 | `E_PATH_REJECTED`，不触碰目标 |
| 空间不足 / 权限拒绝 / 目标占用 | 写入前失败并保留旧版本 |
| 任意步骤失败 | 自动回滚，日志记录已完成步骤 |
| 能力门未通过 | `E_CAPABILITY_BLOCKED`，界面直接禁用按钮 |

## 8. 已知限制

- 内置更新接管：若无法在不破坏签名、不违反官方条款的前提下可靠控制，则该产品**不启用自动更新**，只提供手动检查与官方安装说明。
- 注册表读取依赖系统 `reg.exe`；在受限环境（如企业 AppLocker）被拦截时，扫描会显示跳过原因，而不是静默漏报。
- MVP 不支持网络共享路径与跨磁盘移动。

## 9. 辅助启动（assisted）的边界

本工具在“只读识别”之外，额外提供**按产品 × 按操作**的辅助启动：预检 → 用户确认 → 启动官方交互式界面 → 复扫。
它与自动事务（`installAutomation` / `updateAutomation` / `uninstallAutomation`）是两条独立链路，互不提升权限。

允许：

- 读取并展示卸载命令，但**从不执行**其中的任意参数；只取其中可直接启动的 `.exe`。
- 在安装包通过签名 + 发布者 + 产品身份预检后，以 `spawn(file)` 启动官方安装器/卸载器。
- 启动后重新扫描，用**扫描结果**判断是否有变化。

禁止（代码层面不存在实现）：

- 附加 `/S`、`/silent`、`/D=`、`/quiet` 等静默或自定义路径参数；不拼接、不推测、不传任何参数。
- 模拟点击、注入窗口消息、隐藏官方界面、绕过或自动化 UAC。
- 接管客户端内置更新器、替换其更新源、修改安装包或已安装文件。
- 删除目录、注册表项、快捷方式或用户数据；卸载只调用原厂卸载程序。
- 由渲染进程传入命令、参数或任意可执行路径；IPC 只接受 `product` / `kind` / 安装包绝对路径 / 扫描结果中的实例 id。

发布者基线：

| 级别 | 来源 | 允许的用途 |
| --- | --- | --- |
| `verified` | 证据包 `authenticode.subject` | 参与自动事务判定 + 辅助启动 |
| `observed-install` | 本机已安装主程序的签名发布者 | **仅**辅助启动（不足以授权无人值守写入） |
| `none` | 两者都没有 | 拒绝启动（fail-closed） |

结果判定：

- 进程退出码、窗口关闭、安装器自报成功都不作为依据；只有复扫确认目标变化且另一版本未变，才标记 `launched-and-verified`。
- 复扫无变化、另一版本也变化、或无法判断时，一律 `launched-not-verified`，并在界面提示人工核对。
- 多副本更新一律降级为人工指引，因为没有证据表明官方安装器可被可靠约束到指定目录。

## 10. 受管部署（解包安装 / 更新 / 卸载）

v0.2.0 的主流程不再是“启动官方安装器”，而是**把官方安装包解包后部署到版本化目录**。

信任链：

1. 安装包先过 `verifyPackage`：SHA-256 + Authenticode 状态 + 发布者 + 包内产品名。
2. 发布者基线按 `evidence → user-approved → observed-install → none` 选择，`none` 直接拒绝。
   `user-approved` 只能由用户在确认框中显式同意后写入 `state/signer-trust.json`，不存在自动信任路径。
3. 解包使用随包分发的 7-Zip Extra 26.04 (`resources/7zip/7za.exe` 及配套 DLL)，只做 `list` 与 `extract`，**从不执行归档内的任何程序**；不安装到系统、不写注册表。
4. 解包结果必须包含 `resources/app`（`package.json` / `product.json` / `app.asar`），否则 `E_PACKAGE_FORMAT`。
5. 部署走 `FileTransaction`：`create` 步骤拒绝覆盖已存在目标；失败自动回滚并删除本次创建的目录。
6. 部署后核验：读目标目录的产品元数据 + 主可执行文件存在性，核验不通过即回滚。

隔离保证：

- 安装目标必须位于管理根目录内（`PathGuard`），且不得与已知实例目录重复。
- 更新是 side-by-side：新版本进入新的版本目录，旧目录不动；失败只影响新目录。
- 卸载只删本工具部署的目录，删除前备份到 `<管理根>/<产品>/backups`；用户数据目录不在任何删除清单内。
- 启动前校验主程序 Authenticode 状态为 `Valid`，否则拒绝。

已知边界：

- 官方包的真实内层结构、是否包含额外安装步骤（注册表、服务、快捷方式）**未实测**；
  解包部署只还原文件树，不复制官方安装器写入的注册表项与快捷方式。这是明确的未交付项。
- `installed.json` / `signer-trust.json` 只存本机状态，不进脱敏诊断的原始路径。

## 11. 归档安全、接管边界与发布者指纹（v0.3.0）

解包工具随管理器携带，无需系统预装。使用官方 7-Zip Extra 26.04 x64；原版 `License.txt` 随包提供。解包前按归档总解压体积 ×2 + 200MB 做空间预检，不足直接 `E_SPACE`。

归档安全（写盘前）：

| 检查 | 规则 | 失败处理 |
| --- | --- | --- |
| 路径穿越 | 含 `..` 路径段 | 拒绝整包 |
| 绝对路径 / UNC / 设备命名空间 | 盘符、双斜杠开头、问号或点设备前缀 | 拒绝 |
| Windows 保留设备名 | CON/PRN/AUX/NUL/COM1-9/LPT1-9 | 拒绝 |
| 链接条目 | Attributes 含 l / L | 拒绝（不部署链接） |
| 重复条目 | 大小写不敏感重复 | 拒绝 |
| 条目数 / 解压体积 / 深度 / 路径长度 | 6 万条 / 8GB / 32 层 / 512 字符 | 拒绝 |
| 解包后复核 | 条目必须落在解包根内、无重解析点、累计体积不超限 | 拒绝并清理 staging |

完整应用树（部署前与部署后各校验一次）：主可执行文件 + 应用代码（`resources/app.asar` 或 `resources/app/package.json`）+ Electron runtime（顶层 DLL / `.pak` / snapshot）。缺任何一类都回滚。

接管（adopt）边界：

- 接管只写登记，不移动、不覆盖、不删除、不修改客户端文件或注册表；`releaseInstance` 只删登记。
- 接管前二次校验：目录存在且不是重解析点、产品元数据与目标产品一致、主程序存在、Authenticode 有效。
- 接管实例不允许由本工具删除文件（`uninstallInstance` 返回 `E_TARGET_NOT_MANAGED`），只能移除跟踪。
- 更新接管实例走并排部署：新版本进管理根目录，原安装目录原样保留。

发布者基线：

- 顺序：证据包 → 用户本机确认 → 已安装主程序签名 → 无基线拒绝。
- 用户确认写入 `state/signer-trust.json`，可随时删除重置。
- 基线按证书指纹（thumbprint）匹配：主体名称相同但指纹不同（证书轮换）一律拒绝，避免同名证书被永久信任。
- 签名读取在受限子进程环境下可能拿不到系统安全模块，此时回退到 .NET 证书 API 加离线链校验；仍失败则明确报「签名读不到」，绝不默认通过。


## 12. 原位更新与官方卸载器（v0.4.0）

原位更新（`replaceInstanceInPlace`）：

1. 目标目录必须通过 `PathGuard`；已接管实例位于管理根之外时，仅通过 `externalRoots` 精确放行**它自己那一个目录**。
2. 更新前完整备份到 `<管理根>/<产品>/backups/<操作号>-before`，备份失败即中止。
3. 新版本先解到 staging，再复制到目标同级的 `<目录>.new-<操作号>`（同卷），保证后续重命名是原子的。
4. 交换 = `rename(目标 → <目录>.old-<操作号>)` + `rename(.new → 目标)`；绝不做“先删旧版”。
5. 任一步失败或校验失败：新目录挪到 `<目录>.failed-<操作号>`，旧目录换回原位，并如实返回失败。
6. 运行中检测：更新前只读列出进程，命中目标目录即 `E_BUSY`，不强杀。

官方卸载器（`uninstallAdopted`）：

| 检查 | 规则 |
| --- | --- |
| 登记匹配 | 只接受 `UninstallString` 中可执行文件位于**该实例目录内**的登记 |
| 唯一性 | 多条登记指向同一目录 → `E_CONFLICT`，不猜 |
| 命令行解析 | 结构化解析；仅放行 `/currentuser`、`/allusers`，其余参数（含 `/S`）拒绝 |
| 可执行文件 | 必须存在、Authenticode 为 Valid、产品标识含 workbuddy |
| 执行方式 | `spawn(exe, args)`，不经过 shell，不拼接字符串 |
| 结果判定 | 进程退出码不作为成功依据；轮询最多 60s 确认目录消失，否则 `E_BUSY` 并保留跟踪记录 |
| 数据边界 | 本工具不删除用户数据；官方卸载器是否保留取决于它自身，界面明确说明 |

注册表读取（`PowerShellRegistryReader`）：

- 用 .NET `RegistryKey` 只读三个卸载视图，不依赖 `reg.exe`（本环境 reg.exe 被安全策略拦截）；
- 只读 `DisplayName / DisplayVersion / Publisher / InstallLocation / DisplayIcon / UninstallString` 等值；
- 失败时回退 reg.exe，两者都失败才把原因显示在诊断里。

官网跳转：

- URL 由主进程按 `ProductId` 查表生成，渲染进程只能传产品 id；
- 只打开固定 HTTPS 首页，不含下载直链、API 或查询参数。


## 13. 自动登记（v0.5.0）

扫描后自动把合格的既有安装登记为可管理实例，**不需要用户确认**，因此门槛必须严格：

| 检查 | 规则 | 不通过时 |
| --- | --- | --- |
| 产品归属 | 元数据 productName/applicationName 与产品匹配（`identity === "identified"`） | 不登记，行内显示原因 |
| 管理器自身 | `isManagerSelf` 为真 | 不登记 |
| 冲突标记 | `needsReview` 为真（元数据异常/重解析点/版本不一致） | 不登记 |
| 安装目录 | 存在、是目录、不是重解析点 | 不登记 |
| 主程序 | 目录内存在，且排除 `Uninstall*`/`Repair*`/`Update*`/`Crash*` | 不登记 |
| 主程序签名 | Authenticode 为 Valid | 不登记 |

登记行为边界：

- 只写 `state/instances.json`，不移动/覆盖/删除/启动任何客户端文件，不写注册表、快捷方式、更新配置或锁文件。
- 幂等：同一真实目录（大小写与斜杠归一化）永远得到同一 `instanceId`，重复扫描不会重复插入。
- 补偿校验：本轮扫描没有线索但登记过的目录，会重新校验目录/主程序/签名；失败保留登记但标 `verified=false`，界面显示「未核验」。
- 多副本：按真实路径分别登记，绝不合并或互相覆盖；同一产品最多一个「默认」实例。

更新时保留维护文件：

- 官方 NSIS 安装目录里的 `Uninstall*.exe`、`version`、`*.msix` **不在**内层 `app-64.7z` 里。
- 原位替换新树后，会从旧目录把这些文件复制到新树（`preservedFiles`），否则更新后无法卸载。
- 复制失败不影响已完成的替换，但会在结果里列出保留清单，供人工核对。

脚本模式与单实例锁：

- `--e2e` / `--scan-report` 是独立诊断进程，不参与单实例锁；否则用户开着管理器时这些命令会静默退出。
- 两者都必须向 stdout 输出一行结果（成功或错误 JSON），脚本据此判定；无输出即视为失败。
